Context Engineering
& RAG

Start with choosing useful information for a model. Add retrieval only when it improves answers. This is an experiment, not a new AI agent or infrastructure project.

2 weeksOne experimentOne reviewable PRSundays off

Core idea

Question

“How does the chat service handle a failed Board API request?”

Choose context

Find the relevant handler, client, tests and instructions. Avoid unrelated files.

Answer with evidence

Give a grounded explanation, cite file paths, and say what is unknown.

Experiment: same question, three contexts

A · No context

Ask the model without repository files. Record guesses and uncertainty.

B · Broad context

Include as many relevant repo files as fit the same model limit. Track truncation and noise.

C · Selected context

Include only the handler, client, tests and necessary config. Compare groundedness and efficiency.

Keep the model, question, temperature, and evaluation rubric consistent. Repeat runs where output varies. Do not assume selected context wins: measure it.

What to measure

Correctness

How many claims are supported by actual source files?

Efficiency

Input tokens and latency per run; record model and hardware/provider.

Retrieval quality

Were the needed files or chunks found? Where did search fail?

PR acceptance criteria

  • Document three representative questions and the expected source evidence.
  • Include A/B/C inputs, outputs and a simple score table.
  • Explain one failure case, one tradeoff, and when RAG is unnecessary.
  • Include a reproducible script or instructions; do not claim improvement without data.

Scope: Use an existing PPT repository. No new agent, vector database, or gateway is required. A small local retrieval prototype is enough. This module replaces the introductory architecture lesson as the first hands-on learning topic; the remaining roadmap is provisional.
